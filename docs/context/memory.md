## Storage conventions

- `module1_data.duckdb` — table `udl_data` (raw load, current dataset)
- `module1_data_modified.duckdb` — table `udl_data` (transformed copy: `materialize_modified()` applies type overrides CATEGORICAL→VARCHAR / NUMERIC→TRY_CAST DOUBLE and converts target to 0/1, multi-class → `<col>__binary`). `active_db()` returns this when present, else the raw file.

## Verified library API (from wheel source, `builder.py` — `StrategicSegmentBuilder`, supports `persist_db` single-artifact mode + `close()`/context-manager)

NOTE: `builder.py` now seeds `OptimalBinning(random_state=42)` so `optimal_cart`/`optimal_quantile` fits are deterministic across runs (was previously run-to-run variable — pre-existing OptBinning CART variance, not introduced by the refactor).

## CRITICAL gotchas
 1. **`evaluate_final_coverage()` — library is now safe under `persist_db=True`.** Previously the concern was a DuckDB file-lock from a shared open handle, but `extract_segments` now closes its own connection inside `finally` before returning (and `evaluate_final_coverage`/`generate_feature_health_report` re-open their own connection to the persisted artifact), so calling it from library code no longer hangs. **M3 now calls `builder.evaluate_final_coverage(run["data_path"])` directly** (zero-copy, reads the persisted artifact) — the old UI-side `compute_coverage_local` was removed. M1 persists profiling to JSON (`module1_profiling.json`); M4's `build_scorecard`/`generate_feature_health_local`/`render_diagnostics` accept the DuckDB file path (`active_db()`) and operate via ATTACH — no full pull.
2. Library logger name: `StrategicEngine` (that's what M3 hooks to capture logs into the console).
3. UI validation is deliberately stricter than the library (min_events ≤ min_sample_size, naive_bins ≥ 3, target not in groups/ignore, ≥1 rule type) — keep these guards.
4. Scorecard decile warning: `StrategicSegmentScore` needs ≥10 distinct weights (S:156-164) → guide users to `max_segments ≥ 10` for Module 4.
5. `MAX_JOBS = max(1, os.cpu_count() or 4)` used for the n_jobs widget; `-1 (all but one core)` label ↔ value -1 mapping via N_JOBS_MAP/RMAP.
6. **`explain_feature_journey(feature)` prints to stdout and RETURNS None** — to show it in Streamlit, wrap the call in `contextlib.redirect_stdout(io.StringIO())` and read the buffer. (`explain_no_segments()` correctly returns a string.)
7. **Plotly `go.Sunburst` with `branchvalues="total"` requires every parent `value` == sum of its children's `values`.** Setting groups/root to 0 while children have counts makes the chart render nothing. Accumulate group + root counts from the segments. Rule complexity = # of feature predicates AND-ed in a rule (1-way/2-way/3-way).
8. **Stale/labeled `binning_method` in stored configs breaks M4 diagnostics.** `StrategicSegmentBuilder.__init__` is the ONLY constructor arg that raises (ValueError on non-canonical `binning_method`); it lowercases but does NOT strip spaces, so `"Optimal (CART)"` (the M2 widget label) ≠ `"optimal_cart"`. Older runs / rows duplicated from them may hold labels. Fix: `_normalize_cfg()` in M4 maps labels→values and validates enums before reconstructing the builder for Feature Journey / no-segments. `build_params()` already normalizes on save; the danger is pre-existing `suite_data.db` rows.
9. **Leaderboard date filter (historical).** `read_all_experiments()` returns rows DESC. The old default date-range used `dates[0]/dates[-1]` which, with DESC ordering, produced an inverted range hiding all rows ("No experiments match the current filters"). This is now moot — the date picker was removed; experiments are grouped/filtered by `dataset_name` (Dataset dropdown) and ranked by KPI instead.

10. **Materialized modified dataset vs. session overrides.** M1 `materialize_modified()` is the ONLY thing that changes real DuckDB column types (CATEGORICAL→VARCHAR, NUMERIC→TRY_CAST DOUBLE) and the target 0/1. Storing `type_overrides` in session alone does NOT change types — you must click "Apply metadata & create modified dataset". Every downstream read (M1–M4, and M2) goes through `active_db()`, which returns `module1_data_modified.duckdb` when it exists, else `module1_data.duckdb`. `db_write` still writes only the raw file.

11. **Global `width=` change.** Across `app.py` and all six pages, every `use_container_width=True/False` was replaced with `width='stretch'` (full-width) or `width='content'` (natural width). `use_container_width` no longer appears anywhere under `rapidsegment/ui/`.

12. **Circular-import deadlock in `rapidsegment/ui/__init__.py` — DO NOT REVERT.** Never put an eager `from .app import run_ui` (or any `from .app import ...`) back into `rapidsegment/ui/__init__.py`. `app.py` (the Streamlit entry) imports its siblings `rapidsegment.ui._exit` and `rapidsegment.ui._theme` at module top; importing either triggers the `rapidsegment.ui` package and thus `__init__.py`, and an eager `.app` import re-enters `app.py` while it is still initialising under Streamlit's multipage loader → `_DeadlockError: deadlock detected by _ModuleLock('rapidsegment.ui._theme')`. The fix keeps `run_ui` lazy via a package-level `__getattr__` (PEP 562). The CLI (`from rapidsegment.ui import run_ui`) and the `rapidsegment-ui` console script still work. Keep `app.py`'s sibling imports as `rapidsegment.ui._<mod>` (they only trigger the now-safe lazy `__init__`).

 13. **Streamlit DOM selectors for theming (verified against the installed bundle).** Streamlit does **NOT** emit `.stSuccess` / `.stError` / `.stWarning` / `.stInfo` / `.stException` class names, nor the BaseWeb `data-baseweb="tag"` attribute (confirmed by grepping `.venv/.../streamlit/static/static/js/Multiselect.*.js` — those strings are absent). Use instead: alerts → `[data-testid="stAlert"]` (and `[data-testid="stAlert"] *` to override the inner `<span>` text color); multiselect selected chips → `[data-testid="stMultiSelectTagsContainer"] [data-tag]` (each selected value is a chip element carrying a `data-tag` attribute; its text is `e.colors.white` on an `e.colors.primary` emerald fill). Readability fix in `_theme.py`: both force `color: #001014 !important` so bright-emerald fills show dark text (white-on-emerald was unreadable — e.g. Leaderboard "Status → completed" tag and "Features to profile" tags). **Success alert (Leaderboard "🏆 Best performer", `st.success`):** target it specifically via `[data-testid="stAlertContentSuccess"]` (Streamlit keys the inner content by capitalised kind — `ErrorElement.js` builds `data-testid:"stAlertContent"+i`, `i` = "Success" for kind "success") and its container `[data-testid="stAlertContainer"]:has([data-testid="stAlertContentSuccess"])`; set `background-color: #34D399 !important` for a BRIGHT emerald fill + `color: #001014` black text. Do NOT use `.stSuccess` (never emitted) and don't override the shared `[data-testid="stAlert"]` background (that would hit error/warning too).

 14. **NEVER convert the full dataset into a pandas DataFrame. (Hard rule from the user)** The raw/modified datasets can be very large; a full `SELECT *` → `.df()` will materialise the entire table into Python memory and crash the user's PC. pandas is allowed ONLY for (a) bounded previews (≈100 rows, e.g. the Column Metadata editor / `st.dataframe` of a handful of summary rows) and (b) small aggregated profile summaries (M1 profiling JSON, scorecard/coverage/segment tables which are already small). For everything else use DuckDB on the persisted artifact: pass the file path (`active_db()`) and ATTACH/read `udl_data`, or register a lazy VIEW — never `con.register("name", df)` with the whole frame, and never keep the full df in `session_state`. M1 `materialize_modified` and M3/M4 `active_db()`/`build_scorecard`/`generate_feature_health_local`/`render_diagnostics` already follow this; keep it that way.
    - **Raw library users:** prefer passing a **path** to `extract_segments` / `evaluate_final_coverage` / `calculate_and_export_weights` (zero-copy `ATTACH` read-only). Passing a pandas/`DataFrame` still copies the whole table into DuckDB's in-memory store — fine for small data, but for ~2.5M×70 pass a file path. `build_scorecard` now copies only `target + seg_N flags + row id` (not all columns), and the builder's path-mode `input_data_view` is a lazy VIEW, so the full dataset is never duplicated in RAM; on-disk it keeps just `original_df` + `current_df_base`.

 15. **Large-file ingestion (2 GB+) — `File path` + stream-to-DuckDB.** `1_Data_Loader.py` previously hit "File too large" at 2000 MB (app `MAX_UPLOAD_MB` + Streamlit `maxUploadSize`/`maxMessageSize`). Both caps are now 8000 MB and the drag-drop hard `st.error` is a soft warning pointing to **File path** (the recommended route for multi-GB). The real fix: new `UniversalDataLoader.stream_to_duckdb(db_path, path, encoding)` reads CSV/TSV/Parquet/Arrow **straight from disk** via DuckDB `read_csv_auto`/`read_parquet`/`read_ipc` (no full in-RAM PyArrow table) and ALTERs numeric columns to DOUBLE on-disk. `persist_file_direct(path, …)` in M1 routes CSV/Parquet/Arrow through it; Excel still uses the arrow path. Smoke-tested on a 2058 MB / 4,000,000×51 CSV: loaded in ~76s with only **+23 MB** Python RSS (vs ~1–2 GB if materialised in Arrow). For huge files always prefer **File path** (no browser upload buffer); drag-drop is allowed but browser-buffered.

 16. **Engine resource defaults scale with the host; override for constrained hardware.** Target deployment is **32 GB+ RAM / 16+ cores**, so `StrategicSegmentBuilder.extract_segments` defaults now *utilise* the host: DuckDB `memory_limit = int(80% of total RAM)` and `threads = all-but-two-cores` (or all if ≤4). On 32 GB that's ~25 GB buffer + ~14 threads. Two new constructor params — `memory_limit_gb` (GB) and `engine_threads` (int) — cap on constrained hardware and are plumbed through M2's `run_builder`. Caveat: DuckDB **memory-maps** on-disk DB files (source `udl_data` + workbench `current_df_base`), so RSS also includes reclaimable OS file-cache (~5 GB for 4M×51) not bounded by `memory_limit`. `original_df` is now materialised **lazily** (only in `evaluate_final_coverage`/`generate_feature_health`), removing a redundant full copy during extraction.

 17. **Path-mode coverage/health must accept a string db path.** `StrategicSegmentBuilder.evaluate_final_coverage` and `generate_feature_health_report` take `original_data`; in zero-copy mode M3 passes a **string path**, so they must `ATTACH` it read-only and materialise `original_df`/`input_df` from `__rs_src.udl_data` (like `extract_segments`) — NOT `con.register("input_data_view", original_data)`, which would register the *string* and raise `Python Object "input_data_view" of type "str" not suitable for replacement scans`. The non-string (DataFrame) branch is unchanged. Symptom: `Experiment failed: Coverage computation failed: ...`. Fixed; verified with a string-path unit test (coverage + health both succeed).

 18. **M4 Feature Journey/Health Report lists ALL engine-tracked features (Option A).** `render_diagnostics` derives `feats` from `_tracked_features_from_artifacts(exp_id)` (reads `diagnostics_[-1]["features_state"].keys()` from persisted `result.json` — the authoritative set of every eligible column the builder scored per iteration, excluding ignored features), falling back to `_eligible_features_from_dataset(data_path, cfg)` (dataset columns minus target/pk/ignored). This makes eligible-but-unused features visible/traceable in the Feature Journey dropdown and Health Report multiselect — matching `StrategicSegmentBuilder.features_state` (builder.py:1414–1433) exactly. `_build_diag_builder` stays **lazy** inside the button handlers (no eager re-extraction on page load). Verified: on a 17-column dataset with 5 segments, tracked=16 features vs old module list=13 (segment-used only); non-selected features like `balance`, `day`, `default` now appear; ignored features are correctly absent.
